## 2. Verdict per rule (`docs/RULES.md` order)

### Decision path

**R1. Decides only via trained neural parameters: PASS** (for the components that exist; see R6 for the missing wiring)
- `agent/inference.py:30-34`: forward pass, `FactorizedCategorical(out.logits)`, then `torch.where(self.argmax, dist.mode(), dist.sample(self.gen))`. `self.argmax` is a constant per-head tuple fixed at construction (`:24`); nothing reads the observation to alter an action.
- `agent/model.py:95-103`: policy logits are `nn.Linear` heads on the GRU state. Auxiliary and value heads are returned but not read in `PolicyRunner.act`.
- `env/actions.py:27-39`: fixed index-to-button mapping, same for every input; `env/doom_env.py:209-212` applies it unchanged for `frame_skip` tics. No substitution after the network output.
- Training rollout takes the same route: `train/trainer.py:172-174` (`model.step`, `dist.sample`), `:187` (`env.step(action)`); `train/subproc_vec_env.py:185-186` sends the action chunks to workers, `:67` hands `data[i]` to `train/vec_env.py:69-71` `step_autoreset`, which calls `env.step(action)`. No code between network output and `env.step` changes the action.

**R2. No hardcoded if/else decision trees: PASS**
- No action mask, scripted fallback, stuck-recovery or opening sequence in the files on the inference path (all read in full, listed above). `env/actions.py:4` states "no masking, no observation- or history-dependent logic"; the code matches.
- `if` statements on the path are shape asserts, padding/masking of absent entities (`agent/encoders.py:68-74`), hidden-state reset at episode start (`agent/model.py:89-92`), and the missing-telemetry zero-fill (`env/doom_env.py:300-311`). None selects an action.
- `env/doom_env.py:231-235`: after death/exit the previous observation is returned again; no action is involved.

**R3. No A\*, Dijkstra or other classical pathfinding: PASS**

### Observations

- `env/doom_env.py:81-87`: POSITION_X/Y/Z, kill/item/secret counts and DEAD go only to `InfoVars`; `_build_obs` (`:293-327`) receives `ObsVars` and sensor buffers only. - Absolute heading (`GV.ANGLE`, `:46`, `ObsVars.heading` `:61`) is read on the policy path but consumed only by `ego_motion` (`env/observation.py:201-205`), which outputs body-frame velocity and the turn delta, never the angle. `tests/test_config_and_source.py:201-213` checks invariance to world rotation.

- Engine object ids are used to match entities between decisions (`env/observation.py:166, 175, 185`) and are not written into the features. No sector id, map id or automap anywhere in `agent/` or `env/observation.py`.

**R9. No god-view radar; partial observability only: UNCLEAR**
- Checked and fine: `objects_info` and `sectors_info` default to False (`env/config.py:106-107`), are rejected under EVAL (`:143-146`), and are never read by `_build_obs`. Rays come from the depth buffer of the rendered view (`env/observation.py:91-99`). No automap buffer is enabled (`env/doom_env.py:146-182`).
- Not verified: entities come from `state.labels` (`env/observation.py:151-167`). The PASS would rest on the label list containing only objects that are actually drawn in the current frame. That is the usual ViZDoom behaviour, but no probe or reference note in this repository states it (`docs/reference/engine-probes.md` and `vizdoom-api.md` searched for visibility/occlusion statements: none on wall occlusion).
- Why it matters: `env/observation.py:160-167` still emits `u, v, w, h` and the type for a label with no visible pixel (`d = 0`). `engine-probes.md:223` reports such rows occur (2-18 per about 200 sightings) and attributes them to the weapon sprite covering the entity. If a label could also exist for an object fully hidden behind a wall, those rows would leak positions through walls.
- Owner: `env-engineer` (probe: a monster fully behind a wall inside the view cone must produce no label; or drop rows with no visible pixel).

### Compliant only under OUR interpretation (need organizer confirmation)

- **I1. Entity `u`, `v` screen position** (`env/observation.py:164-165`). `u` is monotonic in the bearing to the entity, so a strict reader could call it a precomputed aim error. It is not in action units, involves no trigonometry and is what a pixel image would also show. ADR 0001 lines 70-76 states the same residual risk. Judgement call: flagged for `advisor`.
- **I2. `du`, `dd` tracked per engine `object_id`** (`env/observation.py:174-185`): uses the engine's identity of an object across frames, which a human player does not get for free.
- **I3. Entity type from engine class names** (`env/observation.py:61-75`) and **keeping the nearest 24 entities when more are visible** (`:168-172`). Hand-written classification and truncation inside the sensor; they filter observations, not actions. ADR 0001 line 73 forbids "sorting by target priority"; nearest-first truncation is close to that line. Flagged for `advisor`.
- **I4. Body-frame ego-motion from absolute ANGLE and VELOCITY** (`env/observation.py:195-207`): trigonometry in the observation pipeline, treated as proprioception.
- **I5. Depth buffer, labels buffer and game variables count as "unmodified engine"**: they are stock ViZDoom API features, not mods, but they are exactly what `+viz_nocheat` removes (E3). Also `map_exit_reward = 1.0` and the HUD/resolution settings under EVAL are treated as harness/sensor plumbing, not rule changes (`env/config.py:60, 235-239`).
- **I6. `+viz_nocheat 1` whitelisted as a vanilla game argument** (`env/config.py:208`).
- **I7. Per-head sample versus argmax fixed by configuration** (`agent/inference.py:24, 33`): sampling from the network's distribution is counted as "decided by trained parameters"; the choice is a constant, not observation-dependent.
